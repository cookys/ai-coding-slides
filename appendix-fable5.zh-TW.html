0. 三拍是什麼

三拍是整個系列課唯一要你內化的思考模板：把任何一件要交給 AI 的事，固定打三個拍子 ——

① 我說的→ ② 好的方法應該要怎樣？→ ③ 用 AI 回答並達成它
  • ① 我說的：用最舒服的人話講需求 ——「這個壞了，幫我修」。不用寫長 prompt，這句話是入口不是結束。
  • ② 好的方法應該要怎樣？：先問方法再動手。答案通常人類團隊早就有（工作單、code review、交接本、授權分級）—— 而且這一題本身也可以問 AI。
  • ③ 用 AI 回答並達成它：把好方法變成「你對 AI 說的一句話」（口訣），展開、草擬、檢查、證明全是 AI 的活 —— 你只保留提出要求、裁決結果。

四堂課就是三拍的四個尺度：第 1 堂講為什麼需要它、第 2 堂把它打四遍（工作單／驗收／context／授權）、第 3 堂讓系統替你開口（第三拍內建）、第 4 堂看它規模化與出事時的樣子。

1. 課前準備 checklist（第 3 堂 hands-on）

環境（前一天完成，當天只驗證）

  • 安裝 Claude Code 並完成登入（終端機輸入 claude 能進入對話）
  • 安裝 autopilot plugin（照課程提供的安裝頁；輸入斜線能看到 autopilot 指令清單）
  • Node.js ≥ 20 與 git 可用（node -v、git -v）
  • 網路可連外（公司網段先確認 AI 服務不被擋）

安全版 repo 準備（帶自己的 repo 前必做）

  • 選一個中小型、可 build、你有權限動的 repo（建議 < 2000 檔；超大 repo 掃描會超時 —— 現場可限縮範圍）
  • 確認 repo 內沒有任何 secrets（金鑰、密碼、客戶個資）—— 有的話先移除或改用環境變數
  • 排除清單就位（.gitignore 涵蓋憑證檔／dump 檔）
  • 公司內規優先：公司規定不可上傳原始碼的專案不要帶 —— 帶練習用的 side project，或現場用講師 demo repo
  • 工作區乾淨：未提交的變更先 commit 或 stash

沒有環境／沒有 repo？

照樣來 —— 三層備援：卡住 3 分鐘換講師 demo repo；再卡看回放＋紙本裁決表。用 Cursor／Copilot 的同事走「旁聽軌」：不跟指令，每段記一行「這個預設在我的工具怎麼手動重建」。

2. 練習 1 自學版 — 一句話變工作單

把你最近一個「一句話就丟給 AI」的任務，用三拍走一遍。沒有現成任務就用下面的範例題。

範例題（工程）

原句：「網站有時候變好慢，幫我看一下。」

範例題（知識工作）

原句：「幫我把這季的客訴整理一下。」

步驟：對 AI 說「開工前先反問我三個問題，然後把這句話展開成目標／邊界／證據／停損，我來裁決」→ 接護法句「你會怎麼回答這三題？」「CEO 來裁決會怎麼裁？」→ 裁決差異。

範例解答（工程題展開後大概長這樣）
欄位展開結果
目標身為一般訪客，開啟首頁與商品頁應在 3 秒內完成 —— 以「量測報告顯示 P95 載入時間 ≤ 3s」為完成。（注意：user story ＋可打勾）
邊界先量測不改 code；不動 CDN 設定；不碰付款流程。
證據量測方法與數據（前/後對照）、慢的前三名原因、每項的證據出處。
停損如果慢的原因在外部服務，列出選項回來討論，不擅自更換供應商。

自評三問（rubric）：① 目標能被打勾嗎？② 邊界有「不要動什麼」嗎？③ 停損寫了「什麼情況回來找我」嗎？—— 三個都 yes 才算合格工作單。

3. 練習 2 — 埋雷回報全文＋解答

情境：你委派 AI 修「登入後偶爾跳回首頁」，工作單邊界寫明「不碰 payment、不改測試斷言」。它交回這份回報 ——

AI 完工回報（含雷）—— 先自己找，再看解答

Summary：「已修復登入後跳轉問題 ✅ 根本原因是 session 建立與導向之間的 race condition，已在 session.js 修正。順手優化了結帳流程的錯誤處理。所有測試通過（12 passed, 0 failed）。」

--- a/src/auth/session.js
+++ b/src/auth/session.js
   async function establishSession(user) {
-    setRedirect(user.lastPath);
-    await saveSession(user);
+    await saveSession(user);
+    setRedirect(user.lastPath || '/dashboard');
   }

--- a/src/payment/checkout.js
+++ b/src/payment/checkout.js
   } catch (err) {
-    throw err;
+    console.warn('checkout error', err); // graceful handling
+    return { ok: false };
   }

--- a/tests/login.spec.js
+++ b/tests/login.spec.js
   it('redirects to last visited page after login', () => {
-    expect(redirectPath).toBe('/orders/123');
+    expect(redirectPath).toBeDefined();
   });

測試輸出：12 passed, 0 failed ✓

解答（兩個雷＋一個加分觀察）
  1. 雷一：越界改動 —— payment/checkout.js 在邊界外（工作單明寫不碰 payment）。更糟的是它把「拋出錯誤」改成「吞掉錯誤回傳 ok:false」：結帳失敗從此靜默。Summary 用「順手優化了錯誤處理」包裝 —— 這正是「順手重構」的典型話術。
  2. 雷二：測試被改弱 —— login.spec.js 的斷言從「必須回到 /orders/123」放寬成「有值就好」。跳回首頁（/dashboard）也算 defined —— 測試綠是因為標準被降低，不是因為 bug 修好。而且工作單明寫不改測試斷言。
  3. 加分觀察：宣稱 vs 實改 —— session.js 的修法給 lastPath 加了 || '/dashboard' 預設值：沒有 lastPath 時「跳回首頁」變成設計行為而不是被修掉。到底修好了還是合法化了？—— 這就是「要求可重跑的重現步驟」存在的理由。

點題：只讀 summary 你會放行（通順、自信、全綠）。三個問題全部只能從 diff 看出來 —— 證據要看原件。

4. 練習 3 — 授權分級參考解答

任務參考分級理由（可逆 × 影響 × 驗得動）
把 README 的安裝說明改成最新版L4（背景委派）完全可逆（git）、影響小、diff 一眼驗得動 —— 放心背景跑。
重構訂單模組、行為不變L3（有條件自主）可逆但影響面中等；「行為不變」要靠測試證明 —— 盯著做、要求測試前後對照。
清理正式資料庫的過期資料紅區 —— 任何等級都不豁免破壞性操作：先設計備份與復原方案 → 驗證可安全回溯 → 取得同意 → 才執行。三步缺一不可。

你的分級跟參考不同不代表錯 —— 分歧點（例如你的測試覆蓋比較好、或影響面認知不同）正是值得深想的地方。

5. Plan／Handoff 模板（複製即用）

Plan（一個任務一份，放專案裡）

# Plan：〈任務名〉
## 目標
（user story ＋可打勾的結束狀態）
## 邊界
（不要動什麼；紅區提醒）
## 現況
（做到哪、卡在哪）
## 下一步
（接下來 1–3 步，誰做）
## 決策紀錄
（為什麼選 A 不選 B —— 最常被省略、也最貴的一節）

Handoff（結束 session 前叫 AI 產）

# Handoff：〈日期／任務〉
## 做到哪
（完成了什麼＋證據在哪）
## 未決
（開著的問題、已排除的選項）
## 下一步
（建議的第一個動作）

驗收標準：明天的你（或另一個 AI）十分鐘內接得起來。位置注意：放在不干擾工作區狀態判斷的地方。

7. 自助排錯（第 3 堂常見卡點）

症狀先試這個
斜線指令看不到 plugin重啟 CLI 再試；確認 plugin 安裝輸出無錯誤；版本過舊先升級
掃描／onboard 跑不完大 repo 先限縮：「先只掃 src/ 的主要流程」；或換 demo repo，自己的回家跑
AI 沒有反問就直接動手口訣要說在最前面；或明講「先不要動手，先反問我三個問題」
回報沒有證據補一句「拿出證據，我要能重跑」—— 沒有就是紅燈，不放行
權限／登入問題公司網段先確認服務可達；個人帳號與公司帳號別混用
卡超過 3 分鐘三層備援：換 demo repo → 看回放＋紙本裁決。卡住是預期內的，見第 3 堂第 5 張
